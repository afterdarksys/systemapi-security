# secsvc hardening, batch 2: contract

2026-11-23. This batch takes the items left open by batch 1 (`hardening-1.md`). Ryan approved it on 2026-11-23 as step 3 of 4. Branch: `fix/hardening-2`, based on `fix/hardening-1`.

Every fix below comes with:
- a test that fails if the fix is reverted;
- a `Threats:` note in the code it changes;
- a stable refusal code from `internal/codes`.

## Changes

| # | Problem | Change |
| --- | --- | --- |
| R1 | Every status, audit or verify call reads all of `audit.jsonl` into memory, with no size cap and no rotation. | **Segmented chain.** Rows go to `audit/NNNNNN.jsonl` segments, each capped (default 4 MiB or 20,000 rows). The hash chain continues across segments: the first row of a new segment has `prev` = the last hash of the previous one.<br>**Runtime reads.** Status, `GET /v1/audit?limit=N` and the in-process tail check read only the newest segment plus `audit.head`. The runtime check verifies the newest segment, and that its first row links to a `segments.json` index. The index holds each closed segment's first seq, last seq and last hash, and is written atomically like the anchor.<br>**Full verify.** `audit verify` (CLI and `GET /v1/audit/verify`) walks every segment with a bounded buffer, and is the one that detects a rewritten old segment. It is a heavier operation: rate-limit it to once a minute through the API.<br>**Retention.** Optional `audit_keep_segments` in the config (default: keep all). Pruning drops the oldest segments and keeps their index entry, so the chain stays anchored. Every prune writes an `audit.pruned` row naming the dropped range and its last hash.<br>**Migration.** None: an existing single-file chain must be moved with an explicit `secsvc audit migrate --dir D`, which refuses while a daemon holds the store. It splits the file into segments, verifies the whole chain, writes the index and anchor, and appends `audit.migrated`. A daemon that finds the old layout refuses with `audit_layout`.<br>We are the only users, so breaking the format is fine. Add a migration note to README "Breaking changes". |
| R2 | Truncation and rewrite of the chain are only detectable locally; root can rewrite both files. | **Off-host anchor, secsvc side only.** `GET /v1/audit/head` (needs `security.audit`) returns `{host, seq, hash, segment, time}`, signed by an anchor key that secsvc generates at first start (`anchor.key`, 0600, O_EXCL; its public key is in status). It also accepts `POST /v1/audit/witness`, which needs a new entitlement `security.witness` and a lease-spending grant. The body is a witness record `{seq, hash, witness, time}`, which secsvc stores in `witness.jsonl` and checks at runtime: the chain must still contain that seq with that hash, otherwise `audit_truncated`.<br>The agent or control-plane side that fetches heads and posts witnesses is a separate systemapi.io batch; this batch defines and tests the secsvc contract. Document it in `docs/architecture.md` and in `docs/CLAUDE-HANDOFF.md`, "Off-host anchor". |
| R3 | Paging leaks the host name, paths and listener addresses to a public ntfy topic. | **Pages carry no host detail.** Each page holds only a severity, a count, a finding-kind summary and an opaque finding id. Host, paths, subjects and addresses stay local (`secsvc call findings`). A config flag `page_detail: true` restores the detail, with a doc warning that the topic is public to anyone who learns or guesses it. A test asserts that the default page body contains no host, path or address. Document that the topic must be treated as a secret. |
| R4 | The API's 10s write timeout can cut off a scan's response while pages are being sent. | Scans send pages asynchronously after the response, through a bounded queue. Each page is audited when sent (`page.sent` or `page.failed`). The response returns as soon as the findings are committed. The write timeout stays at 10s and becomes a tested guarantee. |

## Decisions made during the build

- **R1, layout.** Segments are `audit/NNNNNN.jsonl` (mode `0600`, directory `0700`). The index is `audit/segments.json`, `{"v":1,"segments":[{"first","last","hash"}]}`, one entry per closed segment from seq 1, contiguous; an empty index is not written. `audit.head` keeps its batch-1 shape `{seq, hash}`; the segment is derived. The caps (20,000 rows, 4 MiB) are fixed in code, not config; tests shrink them through package options. A segment rolls before the row that would pass either cap. The index is capped at 1 MiB (about 10,000 segments, 200 million rows at the defaults).
- **R1, roll order.** The closed entry is written to the index before the next segment's first row, so the only crash state is a closed index with no next segment, which opens and continues (tested). A segment past the one the index leaves open is never written by secsvc and is `audit_bad` (tested).
- **R1, runtime reads.** Status, the tail and the head read the anchor, the index, the newest segment and the witness file; an append reads nothing and writes the row, the anchor and, on a roll, the index. The running daemon compares the index with the one it holds and requires the newest segment to end at the row it wrote, so batch 1's "exactly the rows this chain wrote" still holds; an old segment is not read at runtime, and its rewrite or deletion is caught by the full verify only (tested both ways). `GET /v1/audit?limit=N` returns fewer than N rows just after a roll.
- **R1, retention.** The index has no "pruned" field: the chain is the record. Pruning happens only when a segment closes, appends `audit.pruned` `{from, through, last_seq, hash}` before deleting, and needs `keep` of at least one, so the newest `audit.pruned` row is always in a retained segment. The full verify allows missing segments only up to that row's `through`, and only when its `last_seq` and `hash` equal the index entry; deleting a segment without the row, or past it, is `audit_truncated` (tested). A failed delete is not an error for the append that triggered it: the files stay, still verify, and the next roll retries.
- **R1, scope.** `audit_keep_segments` (0 to 1,000,000) deletes history and `page_detail` (R3) publishes subjects, so changing either needs a grant whose watch covers the state directory, otherwise `config_scope`. Both fields are `omitempty` in `config.json` so existing config hashes do not change.
- **R1, full verify.** It streams each segment with a one-line buffer. In the daemon it holds neither the engine nor the store lock: the chain snapshots the index, the newest segment and the witnesses under its own lock and walks the immutable closed segments without it; a prune during a walk appends its row and defers its deletes to the next roll (tested with a hook). One walk runs at a time and each grant actor gets one a minute; anything else is `rate_limited` (429) at once, decided after the grant check and before any read. A clock that moves backwards does not lock an actor out. `audit_layout` counts as an audit failure in caps.
- **R1, migration.** `secsvc audit migrate` refuses a non-empty single-file chain with no anchor (`audit_truncated`) rather than bless it, so a chain from before batch 1 takes `secsvc audit anchor` then `migrate`; `anchor` works only on the single-file layout (`audit_layout` otherwise). The segments are built in a temporary directory and renamed into place; the old file is kept as `audit.jsonl.migrated`, not deleted. Neither file present is a no-op. A crash between the two renames leaves both, which every command refuses with `audit_layout`; the documented recovery is to move `audit.jsonl` aside by hand.
- **R2, key and head.** `anchor.key` is the raw 32-byte seed, created in `store.Open` after the store lock, separate from the grant key. A group- or world-readable key is `seed_perms`; a symlink or a short file is `failed`. The head response is `{"head":{host,seq,hash,segment,time},"sig"}` with `sig` over `secsvc-audit-head-v1\n` plus the compact head JSON. It does not carry the public key, so a verifier cannot be talked into trusting a key from the response; `anchor_pub` is in status. An empty chain's head is seq 0, the genesis hash, segment 0.
- **R2, entitlement.** After review, `security.witness` is carried only by a new purpose, `security:witness` (ceiling `security.audit`, `security.witness`); read, config and operate grants cannot carry it (`grant_purpose`), so no default grant can post a witness.
- **R2, witnesses.** After review, a witness is stored only when the chain holds it now: the row exists and has that hash. A seq past the end or another hash is `witness_mismatch` (409); a row inside a pruned segment other than its last row (whose hash the index keeps) is `witness_unverifiable` (409). A refusal is not stored, does not break the chain, and is audited `audit.witness_refused` with the actor and lease of the verified grant; the `witness` label is data only. This replaces the build-time decision to store a refuting witness, which let any witness grant make the store unopenable with nothing recording who. A stored witness that later stops matching is tampering: open, the runtime read and the full verify fail closed with `audit_truncated`, and `secsvc audit verify` names it (`witness seq N`, second stderr line). The runtime read checks the newest witness and that it is the one the daemon last stored (tested). `time` is capped at 35 characters, the label at 128. Before an append the file is compacted to the newest 500 in at most 64 KiB when it would reach 1,000 lines or 128 KiB, so it never reaches its 256 KiB read cap (the reviewer's 877-witness repro made the store `audit_bad`; the test adds 999 maximal witnesses and reopens).
- **R3.** The default body is `secsvc high KIND: N high finding(s) open, ref PAGEID`. The count is the open high findings after the scan; pages stay one per finding with the existing per-kind coalescing. The page id is 8 random bytes in hex, stored with the open finding (`page_id`, additive in `ids-state.json`) and shown in findings and the report. The report's `id` (SHA-256 of host and subject) was not used because a path can be guessed from it. `page_detail: true` restores the batch-1 bodies unchanged. The test bans the host, the path, its directory, the listener address and port from every default body.
- **R4.** The queue holds 64 pages; `serve` runs one pager goroutine. After review a page has a durable `pending` state: the scan decides each page, marks the finding `pending` and sets the coalesce time, commits, then queues without blocking. `Paged` is set only on `page.sent`. A failed send or a full queue (`queue_full`, a new code) is `page.failed`, and the finding loses `pending` and its coalesce time, so the next scan pages it again. `serve` stops the scan loop, waits for it, then stops the pager; queued pages stay `pending`, and `serve` re-queues every pending page at start (`Resume`, no coalescing). Tested: a crash after the commit, and a stop with pages queued. A crash during a send can send a page twice; a lost page is the worse failure. The audit actions are `page.sent`, `page.failed` and `page.coalesced` (was `notify.*`). The write timeout is a package variable; one test pins it at 10 s, and the slow-page test uses 3 s (room for the scan's fsyncs on a busy disk, below the 5 s send timeout a synchronous page would wait out) and waits for the pager to exit before cleanup.
- **Tests that fail on revert** were checked by reverting each new check in a scratch copy: prune row, runtime index compare, segment past the index, closed-segment end, runtime witness compare, migrate anchor check, legacy layout, verify rate limit, head domain, witness entitlement, witness spend, state-directory scope, retention wiring, anchor key mode, default page body, asynchronous pages, unpage on failure, queue full. All 18 failed as they should.
- **Review fixes** (adversarial review of `bcd77f0`) were revert-checked the same way: witness hash and seq pre-checks, pruned-row refusal, witness purpose, refused-witness audit row, byte compaction, time cap, verify without the engine lock, per-actor limit, one walk at a time, paged only on send, mark sent, resume, pager keeps queued pages, the CLI witness line, and prune deferral during a walk. All 16 failed as they should. The order of stops in `serve` has no unit test of its own; the engine tests cover what it relies on.
